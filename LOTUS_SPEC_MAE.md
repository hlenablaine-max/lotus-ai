## PARTE I — IDENTIDADE E MODELO DE NEGÓCIO

### 1.1 O que é a LOTUS

A **LOTUS AI Enterprise** é uma empresa de **Business Growth & Transformation** que utiliza inteligência artificial como principal força de trabalho. É especializada no setor de saúde (clínicas médicas, procedimentos estéticos, especialidades médicas, grupos de saúde) como nicho primário de entrada, e expande para outros segmentos com a mesma infraestrutura.

**A LOTUS atua em duas frentes complementares:**

**Frente 1 — Crescimento:** Marketing, tráfego pago, copy, criativo, analytics. A empresa gera mais clientes e receita para seus clientes.

**Frente 2 — Transformação:** Implementação de CRM, automações, dashboards, sistemas customizados, receptoras de IA, pipelines de vendas. A empresa resolve os gargalos operacionais que impedem o crescimento.

**Modelo de negócio:**
- Setup: R$10.000 – R$25.000 (diagnóstico + implementação inicial)
- Mensalidade: R$3.000 – R$8.000 (execução contínua)
- Serviços de transformação digital adicionais precificados por projeto

**Proposta de valor única:** Velocidade de execução de IA + profundidade estratégica de consultoria + capacidade de implementação técnica + custo operacional reduzido = resultados superiores.

### 1.2 Posicionamento Estratégico — Healthcare First

O nicho de **saúde** é o ponto de entrada estratégico da LOTUS por motivos específicos:

- Alta margem no setor (procedimentos estéticos, implantes, cirurgias eletivas)
- Baixa sofisticação de marketing da maioria das clínicas
- Alto potencial de transformação operacional (recepção, agendamento, jornada do paciente)
- Regulações conhecidas (CFM, CFO, CFF) que a LOTUS domina
- Ticket médio por cliente: R$5.000–15.000/mês

**Segmentos healthcare prioritários:**
1. Clínicas de estética e procedimentos estéticos
2. Clínicas de cirurgia plástica
3. Clínicas odontológicas
4. Grupos de saúde multi-especialidade
5. Clínicas de medicina do esporte e bem-estar

**Importante:** A arquitetura da LOTUS é agnóstica de segmento. O posicionamento healthcare é a estratégia comercial do Root Master e do LOTUS AI CEO — não limita a infraestrutura técnica. A LOTUS pode atender qualquer empresa que precise de crescimento e transformação.

## PARTE III — O ROOT MASTER (CEO-IA EXECUTOR)

### 3.1 Identidade do Root Master

O **Root Master** é o CEO executor da LOTUS AI. Não é um assistente, não é um chatbot — é o executivo central que:

1. Recebe solicitações de Ícaro (proprietário) sobre clientes
2. Transforma cada solicitação em missões estruturadas
3. Identifica departamentos e agentes necessários
4. Delega tarefas com instruções precisas
5. Monitora execução e qualidade
6. Consolida resultados e entrega ao proprietário
7. Escala para aprovação humana quando necessário

**Domains de atuação do Root Master:**
- Missões de marketing (Growth): campanhas, copy, criativo, performance
- Missões de transformação (BTO): diagnóstico, implementação, automações
- Missões de inteligência (BI): pesquisa, análise, benchmark
- Missões híbridas: combinação de todas as frentes

### 3.2 Protocolo de Resposta do Root Master

**Para solicitações simples:**
- Responde diretamente com autoridade executiva
- Sem floreios, sem disclaimers desnecessários

**Para missões complexas:**
```
1. CONFIRMAÇÃO: "[Entendido] — objetivo confirmado: [X]"
2. PLANO: "Esta missão envolve [N] etapas e [M] departamentos"
3. TIMES: Lista de agentes que serão acionados
4. KICK-OFF: "Iniciando agora com [agente] em [tarefa]"
5. CHECKPOINT: "Vou solicitar sua aprovação antes de [ação irreversível]"
```

### 3.3 Níveis de Autonomia

| Nível | Tipo de Ação | Comportamento |
|-------|-------------|---------------|
| 1 — Operacional | Pesquisa, análise, produção de copy, criação de briefings, diagnóstico, mapas de processo | Executa imediatamente |
| 2 — Condicional | Configurações de campanha, alocação de budget interno, configuração de automações em sandbox | Executa com log registrado |
| 3 — Requer Aprovação Humana | Publicar campanhas, gastar dinheiro real, enviar mensagens externas, contratar, fazer promessas, implementar em produção do cliente | Para, cria Approval, aguarda decisão |

## PARTE IV — SISTEMA DE MISSÕES

### 4.1 O que é uma Missão

Uma **Missão** é a unidade de trabalho da LOTUS. Toda solicitação do proprietário ou cliente se torna uma missão.

**Tipos de missão (expandido):**
- `GROWTH` — marketing, campanhas, copy, criativo, performance
- `TRANSFORMATION` — diagnóstico, implementação, automações, CRM, sistemas
- `INTELLIGENCE` — pesquisa, análise, benchmark, relatórios
- `HYBRID` — combinação de frentes

**Campos obrigatórios:**
- `id` — identificador único
- `clientId` — cliente para quem a missão é executada
- `title` — título executivo
- `description` — descrição completa
- `objective` — objetivo mensurável
- `type` — GROWTH | TRANSFORMATION | INTELLIGENCE | HYBRID
- `priority` — LOW / MEDIUM / HIGH / URGENT
- `status` — PENDING → PLANNING → IN_PROGRESS → WAITING_APPROVAL → IN_REVIEW → COMPLETED
- `tasks[]` — lista de tarefas atômicas
- `documents[]` — entregáveis produzidos
- `approvals[]` — aprovações necessárias
- `dueAt` — prazo de entrega
- `audit trail` — histórico completo de ações

### 4.2 Anatomia de uma Tarefa

Cada missão tem N tarefas. Uma tarefa é atribuída a um agente específico.

```typescript
interface Task {
  id: string
  missionId: string
  agentId: string           // Agente responsável
  title: string
  description: string
  instructions: string      // Prompt específico para o agente
  input: Json               // Dados de entrada
  output: Json              // Output produzido
  status: TaskStatus
  dependsOn: string[]       // Dependências (DAG de execução)
  retryCount: number
  maxRetries: number
}
```

### 4.3 Execução Paralela e Dependências

As tarefas formam um DAG (Directed Acyclic Graph). Tarefas sem dependências executam em paralelo.

Exemplo — Missão Transformação "Implementar AI Receptionist em Clínica":
```
T1: BI → Diagnóstico de processos atuais        (sem dep)  ─┐
T2: BTO → Mapeamento de jornada do paciente     (sem dep)  ─┤─→ T5: BTO → Arquitetura da solução (dep T1,T2,T3)
T3: Healthcare → Regulações e restrições       (sem dep)  ─┘
T5: BTO → Arquitetura (aguarda T1,T2,T3)                   ─→ T6: BTO → Configuração CRM + Automação
T6: BTO → Config (aguarda T5)                              ─→ T7: APPROVAL → Implementar em produção
T7: APPROVAL → Impl. produção (aguarda T6)
```

## PARTE V — SISTEMA DE AGENTES E EXECUÇÃO REAL

### 5.1 Como um Agente Realmente Funciona

Cada agente tem:
- `systemPrompt` especializado (armazenado no banco de dados)
- `department` e `specialty` definidos
- `model` e `provider` configurados
- `tools` disponíveis (browser, search, etc.)
- `permissions` específicas ao seu nível
- `autonomyLevel` (1, 2 ou 3)

**Quando o Root Master delega uma tarefa:**
1. Root Master cria `Task` com `instructions` específicas
2. Task queue executa a tarefa
3. Agente recebe: `systemPrompt` + `instructions` + `context`
4. Agente faz chamada real à IA com esse contexto
5. Output é salvo na `Task.output` e potencialmente em um `Document`
6. Status é atualizado
7. Root Master recebe o resultado e decide o próximo passo

### 5.2 Sistema de Contratação Dinâmica

Quando o Root Master identifica uma lacuna de competência:

1. Detecta que nenhum agente existente tem a especialidade necessária
2. Cria uma `Approval` do tipo `CREATE_AGENT`
3. Aguarda aprovação de Ícaro
4. Após aprovação: gera `systemPrompt` especializado via IA
5. Registra novo `Agent` no banco de dados
6. Novo agente fica disponível para missões futuras

### 5.3 Agent Performance e KPIs

Cada agente mantém:
- `tasksCompleted` — total de tarefas concluídas
- `tasksTotal` — total atribuídas
- `avgQualityScore` — nota média de qualidade (0-10)
- `lastActivity[]` — histórico das últimas atividades

## PARTE VI — LIVE SALES COPILOT *(NOVO)*

### 6.1 O que é o Live Sales Copilot

O **Live Sales Copilot** é o sistema que transforma cada reunião de venda da LOTUS em uma conversa com inteligência completa. Durante uma call com um prospect, o sistema:

1. Recebe a transcrição em tempo real (via integração com Google Meet / Zoom)
2. Identifica participantes (nome, cargo, empresa)
3. Carrega o contexto do CRM sobre aquele prospect
4. Monitora a conversa identificando: objeções, interesse, dúvidas, menções a concorrentes
5. Gera sugestões em tempo real para o vendedor: argumentos, respostas a objeções, próximos passos
6. Registra a memória comercial para uso em futuras interações

### 6.2 Arquitetura do Live Sales Copilot

```
Google Meet / Zoom
    │ (webhook / extensão / API de transcrição)
    ▼
sales_calls (banco de dados)
    │
    ▼
SSE Event Stream → /api/events/sales-call/[callId]
    │
    ▼
Rodrigo Vasconcelos (Sales Intelligence Agent)
    │ Recebe: transcrição parcial + contexto CRM + histórico do prospect
    │ Processa: identifica momentos-chave, gera sugestão
    ▼
call_suggestions (banco de dados)
    │
    ▼
UI do Live Sales Copilot (painel lateral durante a call)
```

### 6.3 Fluxo de Dados em Tempo Real

```typescript
// Evento recebido do Meet/Zoom:
{
  callId: string,
  transcript_chunk: string,
  speaker: { name: string, role: string },
  timestamp: Date
}

// Agente processa e gera sugestão:
{
  callId: string,
  triggerText: string,       // O que disparou a sugestão
  suggestion: string,        // O que falar
  type: 'objection_response' | 'next_step' | 'value_prop' | 'question',
  confidence: number,
  timestamp: Date
}
```

### 6.4 Memória Comercial

Após cada call, o sistema extrai automaticamente:
- Objeções levantadas pelo prospect
- Nível de interesse demonstrado
- Pontos de dor identificados
- Menções a concorrentes
- Próximos passos acordados
- Decisores identificados

Tudo salvo como `Memory` de escopo `CLIENT` vinculada ao prospect.

### 6.5 Suporte Arquitetural Necessário desde F1

O F1 deve criar as tabelas e endpoints, **sem implementar a integração com Meet/Zoom ainda**:
- Tabelas `sales_calls` e `call_suggestions` no schema Prisma
- Endpoint SSE `/api/events/sales-call/[callId]`
- UI básica do painel (sem dados ainda)
- A integração real com Meet/Zoom é Fase 3+

## PARTE VIII — BUSINESS TRANSFORMATION OFFICE (BTO) *(NOVO)*

### 8.1 O que é o BTO

O **Business Transformation Office** é o 9º departamento da LOTUS. Sua missão é diferente dos demais: enquanto os outros departamentos produzem entregáveis de marketing (copy, anúncios, relatórios), o BTO **implementa sistemas e processos que mudam a operação do cliente**.

**O BTO responde à pergunta:** "O que mais está impedindo o crescimento desse cliente além do marketing?"

### 8.2 Escopo de Atuação do BTO

**O BTO implementa:**
- CRM (HubSpot, RD Station, Pipedrive, Salesforce)
- Automações de atendimento (n8n, Make, Zapier, WhatsApp Business API)
- AI Receptionist (bot de triagem e agendamento)
- Patient Journey Intelligence (fluxos automáticos pós-consulta)
- Revenue Operations (gestão de pipeline de vendas)
- Dashboards executivos (Metabase, PowerBI, dashboards custom)
- Sistemas web customizados
- Integrações entre sistemas existentes

**O BTO NÃO implementa:**
- Campanhas de mídia paga (Performance)
- Produção de copy (Copywriting)
- Criação de identidade visual (Creative)

### 8.3 Fluxo de uma Missão BTO

```
1. DIAGNÓSTICO (BI + BTO)
   → Mapeamento de processos atuais
   → Identificação de gargalos
   → Benchmarking de ferramentas

2. PROPOSTA DE SOLUÇÃO (BTO + LOTUS AI CEO)
   → Seleção de solução do catálogo
   → Customização do escopo
   → Precificação via Client Value Assessment

3. IMPLEMENTAÇÃO (BTO)
   → Configuração de ferramentas
   → Criação de automações
   → Treinamento de equipe

4. VALIDAÇÃO (BTO + ASSURANCE)
   → Testes de funcionamento
   → Ajustes finos
   → Documentação

5. ENTREGA (Root Master → Proprietário)
   → Demonstração funcionando
   → Relatório de implementação
   → Plano de evolução
```

### 8.4 Integração do BTO com os Outros Sistemas

- **CRM:** Missões do BTO aparecem no pipeline de cliente como `type: TRANSFORMATION`
- **Sistema de Missões:** BTO usa o mesmo sistema de Tasks e DAG de execução
- **Memória:** Configurações implementadas ficam na memória `CLIENT` para referência futura
- **Approvals:** Implementações em produção sempre requerem Approval Level 3
- **Solution Catalog:** BTO executa soluções do catálogo

- Sessões de browser têm timeout e são encerradas após uso
- Credenciais nunca aparecem em logs

### 20.1 Conflitos Identificados

**Nenhum conflito real foi identificado.** Os 5 novos elementos são expansões da arquitetura, não substituições. Detalhamento:

| Elemento | Interação com v1.0 | Resultado |
|----------|-------------------|-----------|
| Live Sales Copilot | Novo módulo; usa SSE (já existente) | Expansão |
| Solution Intelligence Catalog | Novas tabelas; Root Master tem novo contexto | Expansão |
| Business Transformation Office | 9º departamento; usa missões e agents (já existentes) | Expansão |
| Client Value Assessment | Novas tabelas; agente novo (LOTUS AI CEO) | Expansão |
| Posicionamento Healthcare | Contexto no systemPrompt; Dr. Paulo já existe | Expansão |

### 20.2 Pontos de Atenção (não são conflitos, mas requerem cuidado)

1. **Root Master vs LOTUS AI CEO:** A v1.0 não distinguia os dois papéis. A v2.0 deixa claro: Root Master executa para clientes, LOTUS AI CEO pensa sobre a LOTUS. A interface "CEO Chat" da v1.0 é o Root Master. O LOTUS AI CEO terá interface separada (`/advisor`). Não é conflito — é clarificação.

2. **8 departamentos → 9 departamentos:** O LOTUS HQ 3D precisará de uma nova sala para o BTO. Não é conflito — é adição planejada.

3. **MissionType:** A v1.0 não tinha tipo de missão explícito. A v2.0 adiciona `type` ao modelo de Missão. Será adicionado como campo opcional inicialmente para não quebrar dados existentes.

4. **AgentDepartment enum:** Adicionar novos valores a enums Prisma é uma migração não-destrutiva. Sem quebra.
